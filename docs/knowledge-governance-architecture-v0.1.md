# 知识治理平台技术架构 v0.1

日期：2026-09-28

状态：架构评审稿；目标设计与迁移方案，尚未实施。
产品依据：[资料治理 Agent PRD v0.2.1](./资料治理Agent_PRD-v0.2.md)、[资料清洗规则定义与基线规则库 v0.1](./资料清洗规则定义与基线规则库-v0.1.md)、[产品设计全貌 v0.2](./资料治理Agent产品设计全貌-v0.2.md)。

## 1. 架构结论

以现有 KnowledgeHub 的知识管理能力为迁移基线，建设统一的知识治理产品：原始资料库保存和浏览来源；治理引擎生成有证据的派生知识；整理后知识库供人按目录、标签、版本查看；发布层按项目、用途、条件形成可撤销的知识视图与切片；Agent 只通过授权查询服务读取已发布结果。以上能力共用项目、身份、权限、版本和审计模型。

首版采用**模块化单体 + 独立后台 Worker**。业务状态、授权判定和发布事务集中在一个后端应用；解析、诊断、验证、索引与投递交给 Worker。旧系统与新产品通过受控 API 和迁移作业衔接，不以共享业务表作为集成接口。

| 旧基线 | 升级方式 | 新约束 |
|---|---|---|
| Vue 2 + Element UI 的目录、知识卡片、标签、有效期等页面 | 复用交互与业务经验，逐页接新 API；前端框架升级另立工程任务 | 原始资料和整理后知识分入口，按钮由服务端有效权限驱动 |
| FastAPI、MySQL、Redis/ARQ、对象存储、百炼检索 | 首版优先复用技术与运维经验 | MySQL 是事实源；缓存和索引可重建，不能决定权限或发布状态 |
| 旧文件、卡片、标签 | 建迁移映射；旧卡片先作为待核验草案 | 来源、来源版本、知识版本、发布快照分别建模 |
| 文件级 allow_agent 开关及按文件名/目录名的检索过滤 | 只用于旧数据迁移和兼容观察 | 新查询按稳定 ID、项目、发布状态、用途、条件及当前授权校验 |
| GeoGrowth 等消费者和内部 API Key | 先建一个真实适配器，逐项目切流 | Agent 必须有安装、项目绑定和单次运行身份 |

旧技术依据位于 KnowledgeHub 项目的 docs/architecture-karcher-kb-phase2-2026-07-06.md、docs/architecture-karcher-ai-agent-access-control-2026-08-05.md 和 docs/prd/prd-knowledgehub-multi-tenant-20260814.md。这些文档针对旧客户系统；目标模型以本仓库 PRD 为准。特别是旧多租户设计中的公共 tenant_id='000000' 和 NULL 历史数据，只能作为模板或迁移输入；客户正文、知识和 Agent 运行记录不允许公共租户回退。

## 2. 系统边界与模块

~~~mermaid

    U[知识工作台 / 运营界面] --> API[FastAPI 业务 API]
    A[外部 Agent / 旧消费者适配器] --> API
    API --> AUTH[身份与策略]
    API --> SRC[来源与知识]
    API --> GOV[治理与规则]

    API --> OBJ[(对象存储 原件 / 派生文件)]
~~~

平台控制面管理组织、Agent 模板、全局安全策略和脱敏健康指标。组织数据面管理业务项目内来源、任务、规则、知识和发布。每个组织自动创建唯一系统托管 ops 项目，只保存运营配置、作业状态和聚合指标；业务项目正文不自动流入 ops。运营人员访问客户资料须有明确、限时、可撤销的支持授权，读取留在业务项目审计流。

| 模块 | 持有的事实状态 | 职责 |
|---|---|---|
| Identity & Policy | 组织、项目、主体、角色、Agent 安装/绑定/委派、策略版本 | 认证、有效权限、逐请求及逐工作单元授权、撤销 |
| Source Registry | 来源、不可变来源版本、片段、解析覆盖 | 接入、版本识别、原文授权读取、证据定位 |
| Governance | 任务/工作单元、问题、决策、规则候选/版本、修订/验证 | 可恢复诊断、试运行、派生修订、独立验证 |
| Knowledge Catalog | 知识条目与版本、目录/标签、来源链 | 人的知识库浏览、历史版本与证据展示 |
| Publication & Delivery | 发布快照、切片定义/版本、目的地、回执 | 本地生效、条件化读取、投递和撤回 |
| Audit & Ops | 追加式审计、Outbox、预算账本、作业健康 | 追溯、变更通知、成本与失败监控 |

## 3. 权限、租户和即时撤销

资源层级为 Platform → Organization → Project（ops 或 business）→ Resource。旧 KnowledgeHub 的 organization_id 曾表示部门/业务线，tenant_id 表示租户；迁移时先建立映射表，目标组织 ID 表示租户、项目 ID 表示最小隔离单元，部门另建组织单元字段，不能直接重命名旧列。

授权上下文至少包含 principal_id、organization_id、project_id、resource_id、action、target_use、business_date、policy_version 和 request_id。Agent 再携带 installation_id、binding_id、agent_run_id 和 delegation_id。服务端依次核验身份、组织/项目归属、角色能力、安装/绑定/委派交集、资源与数据分类、用途与状态、预算与速率。业务事实确认、规则激活和发布由经过认证的人员在服务端执行；Agent 文本或委派不能代替确认。

隔离覆盖 API、数据库查询、对象读取、索引召回、缓存键、后台作业和投递。项目数据必须有不可为空的项目归属或可沿不可变外键确定项目。仓储层统一添加项目条件，并验证关联对象同项目。对象 ID 即使合法，也先在调用方项目内查找。缓存键包含组织、项目、主体/安装、用途、策略版本和发布版本；不得保留旧系统那种全局禁止文件缓存。

撤销时，在事务内先关闭主体/绑定/委派或来源读取，将关联知识置为 restricted，递增策略版本并写审计与 Outbox；索引清理和目的地通知随后异步完成。正文下载、知识查询与 Worker 每个新工作单元都重新查权威状态。缓存或外部检索故障时拒绝受影响内容。离线副本仅记录撤回请求和回执，不能保证立即销毁。

旧 Agent 检索服务按 (file_name, cat_name) 匹配百炼节点，且禁止列表缓存/数据库读取失败时返回空禁止集。这条路径存在同名映射风险及失败放行风险。新索引必须存稳定 source_version_id、knowledge_version_id 和 project_id；元数据缺失的候选不得进入回答。已认证且在某项目有角色，并不意味着可读另一项目；多租户授权与隔离需分别验证，参见 [AWS 多租户授权指南](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-api-access-authorization/introduction.html)。

## 4. 原始资料、整理后知识与对外切片

1. **原始资料库**：保留来源、每次读取的版本、目录、解析状态、完整原文和未检查范围。原件不因治理任务而覆盖。用户按来源权限查看。
2. **整理后知识库**：展示知识条目、知识版本、适用条件、状态、来源链、目录/标签和修订 diff。能浏览草案的角色与对外读取角色分离。
3. **发布视图与知识切片**：发布快照冻结知识版本集合；切片定义在单个项目内选择目录/标签/条目、用途、受众、有效期和数据分类上限，产生不可变切片版本。切片是已发布集合的受限投影，不使未发布知识可见。链接、API 和 Agent 每次读取都重新鉴权；导出副本记录投递与撤回能力。

知识读取顺序：认证授权 → 项目/切片范围 → 本地已发布且未撤销/受限的版本 → 业务日期与条件 → 来源仍可读 → 候选召回与精排 → 对候选逐条复核权威状态 → 返回结构化结果。上下文不齐、证据不足、同条件冲突或规则结果为 indeterminate 时返回 clarification_required，不选“最新文件”也不由模型补造业务事实。结果含知识版本、发布快照、适用条件、来源定位、未解决事项与限制；引文正文另按来源权限决定。

旧百炼索引可以用于候选召回，但按 doc_name/cat_name 的后置过滤不能作为新产品授权。过渡期若旧索引节点无法映射稳定来源版本 ID，该索引只服务旧入口，不接入新授权查询。索引清理滞后于撤权时，权威数据库仍阻止内容进入响应。检索候选不能直接交给回答模型。

## 5. 治理工作流与规则引擎

~~~mermaid
flowchart LR
    S[来源版本冻结] --> P[解析与定位]
    P --> C[确定性检查 / 候选召回]
    C --> M[受约束语义判断]
    M --> I[发现与问题组]
    I --> R[AI 规则候选 / 人员决策]
    R --> T[规则草案与影子试运行]
    T --> V[派生修订与独立验证]
    V --> H[人员发布确认]
    H --> K[不可变发布快照]
    K --> Q[知识查询 / 切片 / 目的地]
~~~

任务创建时冻结来源版本清单、目标用途、业务日期、规则/处理方法版本和预算，计算 input_snapshot_hash。Worker 按可重入工作单元运行；每单元开始前检查授权、输入哈希和剩余预算，成功后写检查点与消耗。源版本改变、撤权或预算耗尽时暂停相关单元，未检查范围明确记录，不把任务标为完成。

检测先执行 SHA-256、业务有效期、字段和权限等确定性规则；语义模型只处理需要语义判断的候选。所有检测输出 matched / not_matched / indeterminate、证据定位、检测器/模型版本及置信度。缺字段、低置信或冲突不能降级为 not_matched。问题按相同业务命题、相容条件及同项目归并。AI 只创建规则候选；客户选择本次处理、提升项目规则、设置例外或忽略。项目规则需正例、反例、边界例及适用时的例外例进行影子试运行，并经人员确认。检测规则无发布权。

修订只创建派生物，每项绑定来源片段、问题、决策/规则和 diff。验证至少检查源定位、版本一致、规则条件、引用完整、冲突和回归样本；不能只让同一模型自评。发布服务在同一数据库事务中写不可变快照、审计和 Outbox；Worker 至少一次投递并按事件 ID 去重。外部投递不能与数据库写入假装为一个事务；[AWS Outbox 模式说明](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)也要求消费者处理重复消息。

## 6. 数据模型与一致性

当前 PRD 建议 PostgreSQL + RLS；旧 KnowledgeHub 使用 MySQL。为复用已运行的服务和迁移路径，**首版暂定 MySQL 8**，由应用层强制项目过滤、组合外键/唯一约束、授权集成测试和数据审计保证隔离。该方案没有数据库 RLS。若试点合同要求数据库级租户隔离，实施前须选择 PostgreSQL 或租户独立库，不能把 MySQL 方案描述为具备 RLS。最终选型取决于试点安全要求。

| 数据族 | 关键实体与约束 | 迁移来源 |
|---|---|---|
| 租户与身份 | organizations、projects、principals、role_bindings、agent_installations、agent_project_bindings、delegations、agent_runs；每组织唯一 ops | 旧用户/组织/角色需要 ID 映射及权限重算 |
| 原始来源 | sources、source_versions、content_segments；来源版本哈希和对象 URI 不可变 | 旧 knowledge_files 映射为来源和首个版本，无法定位的旧片段标未检查 |
| 治理 | tasks、task_work_units、issues、issue_evidence、decisions、rule_candidates、rule_versions、rule_tests、revision_sets、validation_runs | 新建；旧标签/有效期只是候选元数据，不自动变成已确认规则 |
| 知识与交付 | knowledge_items、knowledge_versions、publication_snapshots、publication_entries、destinations、delivery_attempts | 旧卡片可导入草案；缺证据或确认链的内容不能直接发布 |
| 切片扩展 | slice_definitions（项目、选择器、受众、用途、状态）、slice_versions（定义、快照、解析后的知识版本清单）、slice_access_events | 新建；切片版本不可变，读取仍受实时权限和撤销约束 |
| 追溯与编排 | audit_events、outbox_events、idempotency_records、budget_ledger、index_jobs | 审计追加写；状态变更与 Outbox 同事务 |

跨表约束：证据、规则、修订和知识引用必须同项目；高影响状态迁移必须关联同项目有效人员确认；发布只引用验证通过的知识版本；同一知识键在完全相同条件和业务时段不能同时存在两个 current 版本。修改使用 version/If-Match 乐观锁。对象 URI、索引 ID 与缓存值不是授权事实。审计与对象保留期按项目策略分别执行。

## 7. API、事件和前端契约

沿用 PRD 的 /api/v1、Idempotency-Key、If-Match、分页游标、短期 Agent 运行令牌和统一错误格式。API、MCP 及旧系统适配器调用同一业务服务和策略判定，不复制另一套 Agent 规则。

| 场景 | 入口 | 关键响应与约束 |
|---|---|---|
| 原件接入与查看 | POST/GET /projects/{id}/sources、来源版本详情/下载 | 来源版本 ID、哈希、解析状态、可读范围；正文单独鉴权 |
| 治理任务 | POST /projects/{id}/tasks、GET /tasks/{id} | 输入快照、检查点、覆盖与未检查范围、预算和状态 |
| 决策与规则 | /issues/{id}/opinions、/decisions/{id}/confirm、/rule-candidates、/rules/{id}/trial 和 activate | 外部 Agent 意见只成为线索；试运行不改变正式知识 |
| 修订与发布 | /tasks/{id}/revision-sets、/revision-sets/{id}/validate、POST /publication-snapshots | 派生 diff、验证报告、本地生效和各目的地状态分离 |
| 知识与切片 | POST /knowledge/query；拟增 GET /projects/{id}/knowledge、POST/GET /projects/{id}/slices | 人可浏览目录和历史；Agent 返回发布版本、条件、出处或澄清请求 |
| 授权与运营 | /organizations/{id}/effective-access、Agent 安装/绑定/委派、支持访问 | 页面渲染和 API 授权同源；ops 默认只见脱敏状态 |
| 变化订阅 | GET /changes、签名 Webhook | 仅标识、版本、时间和事件类型；读取正文重新鉴权 |

知识浏览和切片 API/表属于相对当前 PRD 的架构增量，实现前需写入下一版 PRD 和 OpenAPI。前端的“原始资料库”“整理后知识库”“治理任务”“Agent/切片接入”是同一项目的不同视图。Agent 对话只给当前问题所需知识，不承担整库展示。运营平台与客户前端共用 effective-access 结果，但所有业务 API 独立二次校验。

Webhook 只发送事件 ID、组织/项目、资源 ID、版本、类型、时间和签名。消费者按 event_id 去重；变更游标在项目内有序，发布、撤销和受限分别表达。目的地“收到”“验证成功”“撤回已确认”是不同状态，失败可幂等重试。

## 8. 部署、恢复与可观测性

首版部署单元：前端静态站点、FastAPI API、ARQ Worker、MySQL、Redis、对象存储、检索索引和外部模型/目的地。API 不在请求线程里做长时解析或诊断。Worker 可横向扩容，但工作单元要有租约、幂等键、检查点和最大重试策略；重试前重验授权、输入版本和预算。Redis 故障会影响排队与非权威缓存，不可让它成为权限数据库；索引故障时知识浏览可读数据库中的已发布记录，语义召回能力标记不可用，不能返回未经校验的旧候选。

观察指标覆盖 API 延迟、任务排队与检查点、解析失败、未检查覆盖、规则误报/推翻、授权拒绝、索引滞后、预算消耗、Outbox 积压以及投递/撤回回执。日志记录 ID、原因码、版本、耗时和成本，不存原文、令牌和完整业务意见。沿用 PRD 的上传持久化后 5 秒内返回、任务状态读取 P95 小于 500 ms；诊断总时长先实测再承诺。备份应包含数据库与对象存储的可对应恢复点，恢复演练检查发布快照、审计和证据链。

## 9. 从 KnowledgeHub 升级的实施顺序

| 阶段 | 工作与交付 | 出口检查 |
|---|---|---|
| 0. 盘点与映射 | 备份旧库，核对租户/组织、目录、文件、卡片、标签、有效期、Agent 开关、百炼索引及消费者；为历史对象生成稳定映射 ID | 每条迁移记录能说明归属项目、原 URI、哈希和可读权限；无法归属的数据隔离待审 |
| 1. 身份与项目骨架 | 建组织/项目/ops、人和 Agent 主体、有效权限、安装/绑定/委派；旧 UI 接入新身份上下文 | 跨组织/项目和未绑定 Agent 读取被拒；撤销对新请求立即生效 |
| 2. 原始资料和证据 | 来源版本、对象存储、解析定位、覆盖报告及同项目去重；旧卡片先作草案 | 同名不同内容不混淆；不可解析内容为未检查 |
| 3. 治理闭环 | 任务/Worker、基线检测、问题组、规则候选、人员决策、试运行、派生修订和验证 | 输入变化、预算不足、撤权和规则冲突可暂停/恢复且保留证据 |
| 4. 发布与消费 | 发布快照、知识目录、条件查询、切片、Outbox/投递；接一个真实 Agent 和目的地 | 未发布或失权内容不可答；本地发布与下游验证分别可见 |
| 5. 切流与退旧路径 | 新旧结果对照，逐项目切消费者；停用旧全局 API Key 和 allow_agent 查询路径 | 无按文件名授权、无失败放行；具备回到旧只读入口的预案 |

迁移期间旧系统维持原权限边界，新系统不能借旧 API 获取超出本项目授权的正文。切流前至少跑通：新客户价/老客户合同价/渠道待确认、同名不同内容、原件撤权、索引延迟、Worker 重试和目的地失败。旧数据缺证据时只保留为来源或草案，不补造人员确认、规则和发布记录。

## 10. 必须确认的实施决策

1. 首个试点是否要求数据库级租户隔离。这决定继续采用 MySQL，还是在实施前采用 PostgreSQL/租户独立库。
2. 旧 KnowledgeHub 中租户、部门和历史公共数据如何映射为新组织/项目，哪些历史记录须隔离待审。
3. 首个真实 Agent 和发布目的地是什么，以及其是否支持撤回回执。
4. 单文件/任务预算单位、额度，项目保留期和失权后的删除时限。
5. 试点资料的脱敏边界、允许的模型供应商和外部处理地区。

这些选择影响配置及迁移方式；项目隔离、证据链、人员确认、派生修订、不可变发布快照和撤权后即时拒读是架构约束。
