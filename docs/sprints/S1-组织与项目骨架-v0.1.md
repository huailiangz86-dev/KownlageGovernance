# S1：组织与项目骨架 v0.1

日期：2026-10-08。状态：第一批后端增量完成，S1 整体进行中。

## 本批交付

| 能力 | 实现与边界 |
|---|---|
| 组织创建 | 同一事务创建组织、唯一系统 ops、组织所有者成员关系、幂等记录、审计及 Outbox；任何一步失败均回滚 |
| ops 保护 | 保留键 ops；唯一约束和 CHECK 禁止第二个 ops 或业务项目占用该键；触发器禁止删除、迁移组织和改变类型；ops 保持 active |
| 业务项目 | 组织 owner/admin 可创建；创建人得到显式 project_owner 绑定；继承组织时区 |
| 人员有效权限 | 同时校验主体、组织、项目、组织成员关系、项目角色及有效期；跨组织、撤销、到期、未授权均拒绝 |
| ops 读取 | 组织 owner/admin 或有效 ops_operator 只能获得 ops:read_metadata；组织管理员不会自动获得业务项目正文读取权限 |
| 幂等 | 按主体、请求路径和 UUID 键去重，保留 24 小时；同键不同内容冲突；重放前重验授权；唯一约束竞争后最多重新执行一次 |
| 审计与事件 | 审计只能追加；Outbox 与业务写入同事务，当前只记录资源类型与 ID；尚未实现事件投递 Worker |
| 数据库 | Alembic 初始迁移、MySQL 连接使用 READ COMMITTED 和 UTC；SQLite 开启外键，供本地验证 |
| 工程检查 | GitHub Actions 配置安装依赖并运行单元测试；本地已验证 25 项，远程 CI 尚未运行 |

## 本地运行

需要 Python 3.12 或更高版本。以下 PowerShell 命令从仓库根目录执行：

~~~powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
~~~

创建独立本地演示数据库：

~~~powershell
New-Item -ItemType Directory -Force migration-output | Out-Null
$env:DATABASE_URL = "sqlite:///migration-output/s1-local.db"
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m alembic check
~~~

MySQL 设计基线为 8.0.16+，依赖其 CHECK 约束强制执行。通过环境变量传入专用开发库连接 URL，格式为 mysql+pymysql://USER:PASSWORD@HOST/DB?charset=utf8mb4；应用连接工厂统一设置 UTC 和 READ COMMITTED。生产 schema 前仍须确认试点的数据库级隔离要求；当前没有数据库 RLS。

不要用 Base.metadata.create_all 替代 Alembic，ops 保护与审计追加限制由迁移中的触发器建立。降级仅在空的测试库中验证，不能作为有数据环境的无损回滚办法。

## 调用约定

当前没有 HTTP 服务或登录入口。领域服务接收已由上游身份验证确定的 actor_id；未来 API 必须从验证后的身份中提取，不能直接信任客户端提交的 actor_id。服务自行管理写事务，每次请求或 Worker 工作单元使用新的 Session：

~~~python
from uuid import uuid4
from knowledge_governance.db import make_engine, make_session_factory
from knowledge_governance.identity import create_organization

sessions = make_session_factory(make_engine())
with sessions() as session:
    organization, ops = create_organization(
        session,
        actor_id=authenticated_principal_id,
        idempotency_key=str(uuid4()),
        name="示例组织",
        slug="example",
        timezone="Asia/Shanghai",
    )
~~~

示例依赖已存在且 active 的 user 主体。后续登录/主体管理负责这一步；本批测试使用明确的模拟主体。

数据库读提交隔离和查询刷新用于避免沿用旧授权状态；它们不构成全链路撤权完成保证。后续 API、Worker、来源读取和缓存仍须在对应动作前重验权限，不能跨请求复用能力判定。

## 与旧项目迁移的关系

- 采用 AIOps 的租户生命周期和运营管理业务概念，建立新组织/项目边界；未照搬旧系统直接写 KnowledgeHub 共库表的集成方式。
- 平台 AIOps 控制面与每组织系统 ops 分开；旧组织 ID 不直接复用为新项目 ID。
- KnowledgeHub 的旧 allow_agent、文件名/目录名查询不进入新授权模型。
- 旧租户到新组织/项目的审批映射、真实元数据导出和首次 dry-run 尚未完成。两个预检工具仍只处理本地导出元数据，不连接或改写生产系统。

## 验证结果

本地通过 25 项测试：17 项身份/项目测试及 8 项旧系统迁移预检测试。

已验证：

- SQLite 上执行真实 Alembic 升级及空库降级/再升级；
- 创建事务原子性、幂等冲突和过期、ops 不可删除/转型/迁移组织；
- 跨组织角色绑定拒绝、组织管理员无默认业务读取、Agent 默认拒绝；
- 撤销、到期、组织停用和管理员降权后重验，包含会话缓存场景；
- 审计追加限制、模型与迁移一致；
- MySQL 迁移 SQL 离线生成包含所需保护触发器。

尚未验证：真实 MySQL 上的迁移、并发请求、触发器运行与授权撤销竞争；GitHub 远程 CI；浏览器端到端流程。
