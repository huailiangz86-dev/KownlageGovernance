# 资料治理 Agent 产品规划方案

版本：v0.1 讨论稿  
日期：2026 年 9 月 27 日  
状态：用于确定产品方向和验证范围，不是开发承诺或最终技术设计。

## 一、产品定义与当前结论

产品暂定名：资料治理 Agent。

一句话定位：通过 AI 主动发现资料问题，通过多轮对话获取少量必要的业务判断，将确认意见转化为可复用规则，执行并验证资料修复，为人和各种 Agent 持续提供有效、可追溯的知识。

产品不是另一个文档问答知识库，也不是把传统管理表格换成聊天界面。核心任务是接走资料整理、核对、修订和持续维护中的大部分工作，而不是生成一份要求客户自己处理的问题报告。

产品同时具有两种形态：

- 面向用户的专用 Agent：主动分析资料，以对话完成澄清、规则确认与修订决策。
- 面向其他 Agent 的开放服务：提供诊断、修复、规则提案、版本和有效知识调用能力，不强迫客户更换现有 Agent。

当前有依据的部分：客户存在手动识别新旧资料、核对冲突和维护有效知识的实际任务；相关产品和研究已经实现其中部分能力。

尚待验证的部分：在客户真实资料上能否稳定减少人工时间，规则能否跨批次正确复用，处理成本是否可控，以及客户是否愿意持续付费。客户有需求不等于自动化比例、产品优势和商业模式已经确定。

## 二、客户与首批场景

### 2.1 优先客户

优先服务已有需求、资料持续变化、业务负责人明确的小团队。个人专业工作者可以使用同一核心能力，中大型企业作为后续产品化方向。

首批客户应具备：

- 已有一批真实工作资料，不需要我们替其创作全部原始内容。
- 经常需要判断新旧版本、适用条件或不同来源的说法。
- 有人能提供业务解释，并对关键知识的发布负责。
- 整理结果会进入实际工作或 Agent 使用过程，而不是仅用于演示。

不优先选择资料从不变化、没有人能判断正确性，或者必须依靠大量定制集成才能开始使用的客户。

### 2.2 第一版场景

围绕一个项目或业务主题，对文档、方案、会议纪要进行一致性检查和持续修订。例如一个产品的功能、报价、交付范围及实施说明。

首批问题类型：

1. 完全重复与近似重复：区分可以合并的信息与必须保留的来源。
2. 新旧内容关系：识别新增、补充、部分替代、全部替代或尚无法判断。
3. 内容冲突：定位不一致的数字、条件、日期、范围和业务口径。
4. 适用性与状态：区分草稿、建议、已批准内容，以及不同客户、项目和生效时间。

首版优先支持文本、Markdown、DOCX、可提取正文的 PDF，以及上述类型的纪要导出。扫描件、复杂表格、音视频等进入后续范围；不能可靠读取的资料必须明确显示，不计入已完成覆盖。

## 三、核心体验：AI 做工作，人做少量决策

### 3.1 用户入口

用户选择资料范围，说明本次目标，例如：

> 整理这个产品的方案、报价和会议纪要，维护当前有效资料，并指出需要我决定的问题。

系统只要求必要的目标和授权，不要求用户先设计文件分类、清洗规则或流程节点。

### 3.2 完整任务闭环

1. 建立资料清单：记录来源、版本、可读取范围和处理预算。
2. 主动诊断：AI 分析问题，寻找依据，并明确检查覆盖和不确定性。
3. 形成处理计划：将确定问题和业务歧义分开，归并可以用同一决策处理的事项。
4. 对话澄清：优先询问会影响一组资料的重要问题，而不是逐条审批文件。
5. 注册规则提案：区分本次例外、项目规则和长期规则，展示适用范围及影响。
6. 修复与验证：在授权边界内执行；检查结果是否符合规则、是否遗漏或引入冲突。
7. 发布有效版本：经必要确认后交付可使用知识，旧内容保留历史或退出当前引用范围。
8. 持续维护：新增资料或规则变化时，只重新处理受影响范围。

### 3.3 示例对话

AI：新版方案与旧资料存在价格和交付周期差异。格式与完全重复项已完成处理；价格差异是否适用于所有客户？

用户：老客户保留签约价，新客户按新版报价；交付周期下个月才生效。

AI：我将价格按客户类型保留两种适用条件，交付周期按生效时间区分。是否将这个原则用于当前项目后续报价资料？还有渠道客户是否另有规则？

用户：只用于这个项目，渠道客户单独询问。

AI：已调整提案。项目规则中加入客户类型与生效条件；渠道客户进入待确认，不推广到其他项目。确认发布后，相关有效知识和版本关系将一起更新。

以上为目标体验，不代表当前已有实现。系统不能仅凭“文件更新更晚”认定业务事实更权威。

### 3.4 对话与可视化的分工

对话是主要决策入口；原文定位、差异对比和版本记录是辅助检查工具。用户可以深入查看证据，但不必先打开管理表格逐条完成整理。

用户离开或暂不回答时，系统只继续执行已有授权范围内的确定动作，保留待确认事项，不把沉默视为批准。

## 四、输出与完成标准

一个任务应交付相互关联的结果，而不是孤立报告：

- 已修复的资料或派生有效版本。
- 可供人和 Agent 使用的知识条目及适用条件。
- 少量待决策问题，以及 AI 已提出的候选判断和证据。
- 已确认规则、本次例外与未确认规则草案。
- 修订记录、来源定位、版本关系与恢复办法。
- 检查覆盖说明：处理了什么、跳过了什么、哪些无法可靠判断。

至少区分三种完成：

- 整理完成：资料已经按规则处理，不代表已经批准发布。
- 发布完成：有效知识进入指定使用范围。
- 同步验证完成：指定下游已获得新版本，不再使用应退出的旧内容。

没有接入下游验证时，不能宣称所有 Agent 已更新。资料质量改善也不能保证下游模型回答必然正确。

## 五、规则体系与自主执行边界

### 5.1 规则不是聊天记忆

规则必须作为可管理对象保存。建议包含：规则内容、目标对象、适用范围、生效条件、例外、来源依据、确认人、版本、允许的动作和验证方式。

区分：

- 本次意见：仅影响当前修订。
- 持久规则：影响后续相应资料，须明确范围。
- 参考偏好：影响表达和组织方式，不授权事实修改。
- 业务事实：进入有效知识，但不自动成为通用处理方法。

规则状态建议为：草案、待确认、试运行、已生效、已替代、已停用。用户批准一次具体修改，不等于批准未来所有相似修改。

### 5.2 规则生效流程

AI 提案后，检查与已有规则是否冲突；用明确样本试运行，展示影响和例外；取得相应确认后发布。新规则应先用于已确认范围，不能未经授权扩大。

规则更新要检查受影响的已有结果。记录来源版本、规则版本和处理方法，支持重新验证与规则撤销。

### 5.3 自主执行分级

| 情况 | 执行方式 |
|---|---|
| 首次分析与规则试运行 | 默认只读，生成提案 |
| 已授权规则内、可恢复的确定处理 | AI 自动执行，记录结果 |
| 事实冲突、业务含义不明或范围不清 | 聚合后通过对话澄清 |
| 删除原件、覆盖正式资料、公开发布或扩大权限 | 由具有权限的人明确授权 |

默认优先修复派生版本，不直接覆盖原始资料。写回原系统是独立能力，需明确权限、版本检查与恢复范围。

## 六、知识层：逻辑汇聚，不先建全量数据中台

| 层次 | 核心内容 | 目的 |
|---|---|---|
| 来源登记 | 位置、来源版本、权限、更新状态 | 发现变化，避免重复接入 |
| 内容与证据缓存 | 解析结果、必要原文快照、段落定位 | 支持检查与修订追溯 |
| 治理状态 | 问题、规则、确认、修订、处理依赖 | 持续维护，而非每次重做 |
| 有效知识视图 | 按用途、时间、条件和权限筛选的内容 | 提供给人和不同 Agent |

原件可保留在客户现有系统。是否缓存正文或快照，由授权和恢复需求决定；仅保存链接或摘要不足以支撑精确修复。

知识条目至少记录出处、来源版本、内容定位、确认状态、适用条件和替代关系。一个文件只有部分内容失效时，不应整篇废弃。

不同客户数据严格隔离；同一客户内部也按权限和业务范围组织。开放能力不等于公开客户资料。

初期不要求全企业知识图谱或统一迁移。根据真实任务建立必要关系，后续再扩展。

## 七、开放能力与其他 Agent 接入

### 7.1 开放的不是一个搜索框

核心服务应可独立调用：

- 提交诊断或修复任务，并指定资料范围与预算。
- 查询任务状态、证据、待确认事项和修订提案。
- 提交业务意见，生成或调整规则草案。
- 按授权执行修订、发布有效版本或恢复结果。
- 获取具有来源、状态和适用条件的有效知识。
- 查询版本变化，接收更新与失效通知。

以 API 为基础，提供 MCP 适配；批量交付、SDK 和其他适配根据实际接入需求扩展。长任务采用后台任务机制，不要求一次聊天调用持续等待。

### 7.2 多 Agent 一致性

所有入口共享同一套任务、规则和知识版本。相同请求重复提交不能导致重复修复；多个 Agent 修改同一资料时，应用前检查版本，出现冲突则暂停合并。

外部 Agent 的文字意见不能绕过确认权限。读取、提案、执行和发布应分别授权，并关联客户与实际发起人。

实时调用可以返回当前有效版本；复制到下游知识库需要同步更新与撤回机制；离线导出无法保证即时收回。响应应说明版本与有效条件，不承诺未接入系统自动服从这些条件。

### 7.3 初期接入策略

先用自己的对话入口跑通任务，再验证一个真实外部 Agent 接入。开放接口从一开始预留，但不先建设插件市场，不承诺兼容所有 Agent。

首个外部接入是否选择 Hermes、现有客户 Agent 或其他系统，以客户实际使用情况决定。

## 八、成本与 Token 控制

不采用“每次新增都全库重读”和“所有文档两两比较”的默认方案。

主要措施：

- 用普通程序识别完全重复、来源变化和可确定的格式问题。
- 分级解析：简单正文先处理，复杂 OCR 和多模态明确单列成本。
- 先筛选相关候选，再对原文做语义比较；重要任务允许扩大检查范围。
- 保存稳定解析结果，增量处理变化内容及其关联影响。
- 已确认规则能够可靠程序化的部分直接执行；歧义再调用模型。
- 缓存键包含来源、规则、解析和处理方法版本，不复用已失效判断。
- 大任务分批处理，记录进度、支持恢复，不依赖无限增长的对话上下文。
- 设置单任务预算，接近上限时解释剩余工作，由客户选择缩小范围、继续或延期。

首次盘点和理解资料可能较贵，无法用增量处理消除。便宜的候选筛选也可能漏检，不能将低成本抽查包装成完整审计。

成本记录应分开：首次整理、日常增量维护、外部 Agent 读取、客户审核与返工、我方支持与实施。

暂不设未经测试的 Token 单价或毛利目标。后续按真实任务测量模型、解析、存储、调用和人工支持的完整成本。

## 九、最小可行版本范围

### 9.1 必须闭环的能力

1. 一个项目范围内的资料导入、来源和版本登记。
2. 主动发现首批问题类型，并定位原文证据。
3. 多轮澄清，区分本次意见与持久规则。
4. 规则提案、范围确认和试运行。
5. 修复派生版本，验证结果，明确待处理事项。
6. 发布有效知识，保留修订历史并支持恢复。
7. 第二批资料的增量处理与规则复用。
8. 有效知识读取与任务查询接口。

### 9.2 第一版明确不做

- 通用聊天助手或另一个全面的 Agent 开发平台。
- 整台电脑优化、系统文件清理和自动删除原件。
- 飞书、企微、Notion、Wiki 等全部连接器同时上线。
- 无证据的事实补全，或“自动认定所有资料真实”的承诺。
- 企业级全量迁移、所有格式支持和复杂组织治理的完整交付。
- 人工编排画布作为普通用户必需入口。
- 公共知识池、跨客户规则或资料共享，以及插件市场。

## 十、分阶段推进与验收

不在团队规模、现有代码和预算未知时给出固定开发日期。各阶段以验收条件推进。

### 阶段 A：真实资料原型

选择一个明确资料集，建立客户认可的正确答案、冲突和适用条件。跑通主动诊断、多轮澄清、规则草案和派生修订。

验收：能定位证据、减少逐份核对；不遗漏声明范围之外的限制；能够承认无法判断。不能依靠我方人员隐藏地代替 AI 完成分析。

### 阶段 B：持久规则与第二批资料

实现任务状态、规则版本、修订记录和增量维护，用未参与规则形成的新资料测试。

验收：减少重复询问，正确识别例外；原文或规则变化时不继续使用失效结果；撤销和恢复范围明确。

### 阶段 C：付费客户试点

建议选择 3—5 个愿意共同验证的客户，不作为市场规模推断。记录现有方法、通用 Agent 和本产品的完整处理成本。

验收：客户在约定质量标准下节省总时间，并愿意为实际交付结果付费；无需每家客户持续重写大量专属代码。

### 阶段 D：外部 Agent 与持续服务

接通一个真实外部 Agent，支持后台任务、变化通知和下游版本验证；根据客户需求增加优先数据源连接器。

验收：下游可正确获取有效版本、识别待确认状态，重复调用不重复修复，权限和确认边界不被绕过。

### 阶段 E：企业扩展

在需求和付费明确后补充组织角色、审批、部署、连接器和审计。企业交付单独计量，防止以企业未来需求拖重初版。

## 十一、试点评估与继续／停止条件

核心指标不是清理文件数量或输出文字数量，而是：在质量不下降的前提下，人工总工作时间是否减少。

评估项：

- 人工时间：准备、澄清、审核、返工全部计入。
- 检测质量：真实问题发现情况、误报与遗漏。
- 修复质量：正确修订、错误修订及新引入的问题。
- 对话效率：是否用少量问题解决一组事项，是否重复询问。
- 规则复用：在未见资料上的正确适用、例外识别与错误推广。
- 新鲜度：更新、发布与下游实际使用之间的时差。
- 完整成本：模型、解析、存储、集成及我方人工支持。
- 商业结果：付费试点、重复使用、愿意维护的范围和续费理由。

比较应使用难度相近的资料，记录使用者经验和通用 Agent 的配置成本；保留独立测试资料，不能只复测已经解释过的样本。

继续条件：约定质量达标，客户人工总时间有实质下降，第二批规则复用有效，成本在客户愿付范围内。

缩小或暂停条件：审核比手动处理更累、关键修订不可靠、规则不能复用，或者必须依靠持续人工代运营才能达到效果。缩小到某类任务仍可成立时，不直接扩张成全能平台。

## 十二、商业模式假设

客户购买的是“持续维护有效资料的工作能力”，不是 Token、报告页数或删除文件数量。

建议验证的收费结构：

- 首次整理：范围明确的付费试点或整理额度，覆盖较高的初始化成本。
- 持续维护：基础订阅包含一定增量处理量，超量或复杂解析另计。
- 开放接入：允许客户用自己的 Agent 调用，计量后台处理与服务，不重复为同一份结果收取整理费。
- 企业能力：私有部署、复杂连接器和实施单独报价，不混入基础工具价格。

实际价格、读取次数与处理量的计费单位暂不确定，须以试点成本和客户购买方式验证。若客户只有一次性整理需求，可以项目收费，不强行订阅。

不承诺免费全量清洗，不以大量定制实施补贴低价订阅，不默认做代整理服务。

## 十三、竞争判断与已有依据

### 13.1 当前差异化假设

需要证明的优势是：面对同样资料和业务意见，完成更多正确处理，让客户少做判断；并在后续新增资料中持续复用规则。

不能单独作为差异化的要素：聊天界面、使用 Agent、版本管理、知识库、MCP 接入、记忆用户意见或“更聚焦”的表述。

重点研究以下产品的实际任务表现，而不是仅比较官网功能名：

- [Slite Agent](https://slite.com/help/WZXHFySavM6T0-/Enable-Self-Maintaining-Documentation)：主动资料维护和修订审核。
- [Hyperagent](https://www.hyperagent.com/docs/learning)：从纠正中提出可持久化记忆、技能和指令更新；这是相邻能力，不等同于已完成数据修复。
- [Cleanlab](https://help.cleanlab.ai/codex/)：从 Agent／RAG 回答中识别问题并交由专家改善；答案修正不等于原始资料修复。
- [TorchV AIS](https://www.torchv.com/docs/manual/ais-wb/)：国内知识治理与 Agent 相关产品；其文档混合标准、可配置和演进能力，需要实测交付版本。

上述为公开资料核查，未完成实际对比测试，也不构成完整竞品清单。

### 13.2 技术参考

- [Cocoon 研究](https://arxiv.org/abs/2410.15547)：语义规则与数据问题检测，支持部分技术可行性，不代表已经验证企业非结构化资料全流程。
- [STACKFEED 研究](https://arxiv.org/abs/2410.10584)：根据专家反馈修订知识库，不能直接推断客户业务事实可以自动判断。
- [CocoIndex 增量处理](https://cocoindex.io/blogs/incremental-processing/)：缓存和来源依赖可用于减少重复计算，不代替语义治理。
- [MCP 工具规范](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/server/tools.mdx)：用于开放接入，不保证客户端自动正确调用或遵守所有业务条件。

## 十四、本轮评审需要决定的事项

1. 是否认同“专用资料治理 Agent＋开放执行服务”的定位，而非新的问答知识库？
2. 首批选择哪一个现有客户、哪一个项目资料集，优先解决哪两类问题？
3. 初期是否只修复派生版本，哪些条件下才允许写回原系统？
4. 客户哪些业务判断可以成为持久规则，谁有权确认？
5. 第一阶段是否先交付整理结果，第二阶段再接一个外部 Agent？
6. 可投入预算和试点验收标准是什么，如何记录人工时间、错误与完整成本？

本稿建议：先证明一次处理能省事，再证明后续资料能正确复用规则，最后证明对外开放后仍能保持质量和权限边界。不要同时建设通用 Agent、全量知识中台和企业集成平台。
