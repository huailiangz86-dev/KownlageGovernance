# 资料治理 Agent：产品设计全貌

版本：v0.2 产品设计讨论稿  
日期：2026 年 9 月 27 日  
基础：[v0.1 产品规划方案](./资料治理Agent产品规划方案-v0.1.md)  
说明：本稿定义目标体验、信息结构和业务约束。概念演示中的资料与数字均为模拟，不表示已有能力、客户数据或实际性能。

## 一、先看到完整产品

产品由一个共享核心和两个入口构成。

- 用户入口：用户交代任务，AI 主动分析，在必要时通过对话获取业务判断，展示处理成果。
- Agent 入口：外部 Agent 通过授权接口提交同类任务、提供意见或读取有效知识。
- 共享核心：资料来源、任务状态、证据、规则、修订和发布版本。入口可以不同，状态不能各维护一套。

核心体验不是“进入知识库管理后台开始维护”，而是“把资料维护工作委托给一个专用 Agent”。资料页、规则页、版本页是检查与控制入口，不是必须逐条操作的工作表。

建议初期采用 Web 工作台，方便个人与小团队共同处理；资料接入通过上传或指定连接器。桌面本地伴侣、企业内网部署属于后续形态，尚未决定。开放服务不是公共资料共享平台。

### 1.1 产品信息结构

| 一级入口 | 用户来这里完成什么 | 首版位置 |
|---|---|---|
| 工作台 | 看 AI 在处理什么、还有哪项业务判断需要自己决定 | 默认首页 |
| 整理任务 | 发起委托、继续对话、查看处理结果 | 核心 |
| 资料来源 | 确认接入范围、原文、读取异常和变化 | 核心 |
| 有效知识 | 检查当前发布内容、适用条件及依据 | 核心 |
| 处理规则 | 看 AI 学到了什么、范围是否正确、是否需要撤销 | 核心但非日常必经 |
| 发布与版本 | 看修订差异、恢复版本、确认下游同步 | 核心 |
| Agent 接入 | 授权调用、任务与版本接口、同步状态 | 基础接口先做，管理页后补 |
| 设置 | 项目、成员、授权、预算、数据保留与通知 | 必要配置，分期扩展 |

项目是初期的工作边界：资料、规则、任务与发布结果先按项目组织。跨项目复用必须重新明确范围，不自动继承。

## 二、角色与责任

### 2.1 个人模式

一个用户可以兼任委托人、业务确认人和发布人。系统仍保留不同动作的记录，不因为只有一人就取消规则范围与高影响操作确认。

### 2.2 团队模式

| 角色 | 责任 | 不能默认获得的权限 |
|---|---|---|
| 委托人 | 选择资料范围、提出目标、提交业务意见 | 修改所有人的规则或公开发布资料 |
| 业务确认人 | 确认本领域事实、适用范围和规则 | 授权访问原本无权读取的来源 |
| 发布人 | 批准知识进入指定使用范围 | 跳过必要业务确认 |
| 管理员 | 配置成员、来源、预算和接入 | 自动成为所有内容的业务权威 |
| 外部 Agent | 在授权范围内提交任务、提案或读取 | 仅凭对话内容发布规则、覆盖原件 |

初期简化为所有者与协作者，并为关键确认绑定实际人员。多角色审批和复杂组织架构后续扩展。

## 三、首次使用与日常使用

### 3.1 首次使用：五步即可发起

1. 创建项目或选择已有项目。
2. 上传一批资料；未来可选择已授权来源中的具体目录。
3. 用自然语言说明结果目标，例如“维护产品报价与交付口径”。
4. 确认范围、读取方式、处理预算和允许的自动动作。
5. 发起后台任务。用户可以离开，系统把需要决策的事项留在工作台。

默认只读诊断，修订在派生副本中完成，不直接覆盖原件。自动动作授权单列，不混入上传确认。

### 3.2 日常使用：不要求每天进入后台

系统在授权周期内检查变化，把新资料分为新增、补充、可能替代、冲突和无法读取等类型。已有规则适用时执行，遇到例外时才询问。

通知只包含需要行动或有实质影响的变化，不为每个文件发送提醒。正常完成可以汇总；阻塞、预算即将耗尽和发布失败应及时告知。

### 3.3 从其他 Agent 使用

用户在现有 Agent 中提出同一委托，由 Agent 调用本产品。需要业务决定时，可以在原会话中澄清，也可以跳转到工作台查看证据。确认身份与权限必须一致，不能将外部模型生成的“用户已同意”当成授权记录。

## 四、各页面的具体设计

### 4.1 工作台：显示委托进展，而不是堆指标

主要内容：

- 顶部委托框：“你想让 AI 维护哪一组资料？”
- 需要你决定：按影响和阻塞程度排序的少量问题组，显示推荐、依据和影响对象。
- AI 正在处理：任务的当前阶段、检查范围、可安全继续的工作。
- 最近成果：已修复、已发布、待下游同步的结果。
- 下方保留项目入口与读取异常，不突出文件数或虚构健康评分。

主动作是“继续处理”，直接打开对应任务。没有待办时显示“当前无需你决策”，同时说明最后一次检查时间和范围，不宣称所有知识永久正确。

### 4.2 整理任务：对话与工作状态并列

建议桌面布局：左侧产品导航，中间任务对话，右侧可展开的证据与影响区域。窄屏改为上下排列。

任务顶部固定表达三个概念：检查范围、当前阶段、原件处理方式。

对话流展示：委托目标、AI 已完成的工作摘要、问题组、用户意见、修订后的规则卡片和执行结果。只展示必要工作记录，不输出冗长的模型思考过程。

证据区域展示原文摘录、来源版本和定位；点击问题后展示双方依据。可按需进入完整差异，但用户不需要为每份资料打开一次。

推荐动作：提供业务意见、采用建议、仅本次适用、设为项目规则、暂缓、查看影响、停止任务。

“采用建议”必须说明采用的是哪项判断及影响，不使用缺少范围的“一键全部修复”。草稿规则可以和批准本次修订分开确认。

### 4.3 资料来源：管理授权与证据，不是手工分类中心

显示：来源名称、接入范围、来源版本、最近检查、读取状态，以及与任务和有效知识的关系。

来源状态区分：可读取、读取失败、权限变化、来源已删除、内容有新版本。已删除或失权来源产生的派生内容，须按授权和保留策略限制访问、删除或归档，不能继续无条件提供。

用户可以追加资料、缩小范围、暂停来源和查看原文；分类与关系首先由 AI 建议。暂停检查不等于删除资料，也不等于所有派生内容立刻失效，界面要解释影响。

### 4.4 有效知识：展示可用依据，而非另一份 AI 摘要

每项知识显示：结论、适用条件、生效时间、出处、确认责任和当前版本。内容可以是文档片段、知识条目或经确认的修订文档，不要求原件全部转换为统一文章。

默认查看当前已发布视图；待确认、历史、未来生效内容可以另看，不能混进当前引用范围。

提供“试读”入口：输入客户类型、业务日期或项目条件，检查本服务会返回什么依据。这是验证资料适用性，不是新建泛问答产品。

当条件不足时返回需要澄清的事项，而不是为了给答案选择一个任意版本。已确认状态代表经过相应确认，不代表系统保证事实永远正确。

### 4.5 处理规则：AI 学到了什么

默认以自然语言规则卡片呈现：规则内容、对象、项目、条件、例外、动作范围、确认记录和试运行结果。

用户可通过对话纠正：“这只适用于 A 项目”“没有批准的纪要不能替代制度”“先暂停这条规则”。系统生成新版本和影响预览，不静默修改已执行历史。

进阶查看才显示具体检查条件、执行方式和验证样本。不是要求客户写表达式，也不把自由文本偏好假装成可靠执行规则。

确定性规则可以由程序执行；语义规则可以调用模型，但仍需作用范围、验证方式和不确定时的处理策略。

### 4.6 发布与版本：看清实际交付

一次发布是相互一致的知识与规则使用快照。显示新增、修改、替代、仍待确认的内容以及验证记录。

发布前展示：允许发布的内容、未解决问题、未来生效内容和目的地。不要求所有问题解决才发布，但未解决事项不得伪装为已修复。

发布后分别显示本地生效、下游已接收、下游已验证。恢复历史版本是一次新发布，重新执行必要权限和验证检查，不简单抹掉当前历史。

### 4.7 Agent 接入：不只提供密钥

连接卡片展示：客户范围、实际调用方、可读项目、可执行动作、当前权限、最近调用和已同步版本。

接入向导依次选择调用目的、授权范围、验证调用，再启用。只读接入不默认获得修订权限。

外部 Agent 可以提交发现的问题；必须标识为未验证线索，再由治理任务查证。产品提供规范化结果，不能保证外部模型不误读或私自缓存。

## 五、核心对象与关联

| 对象 | 保存内容 | 关键关联 |
|---|---|---|
| 项目 | 工作边界、责任、默认预算与授权 | 来源、任务、规则、发布 |
| 来源版本 | 原文位置、版本、权限、读取记录和必要快照 | 证据、知识片段 |
| 资料片段 | 可定位的内容单元及解析状态 | 问题、知识、处理依赖 |
| 问题组 | 问题类型、双方证据、影响和不确定性 | 任务、决策、修订 |
| 决策 | 原始业务意见、解释、确认人和范围 | 规则提案、本次修订 |
| 规则版本 | 条件、动作、例外、证据和验证方法 | 试运行、修订、任务 |
| 修订集 | 修改前后、适用规则和来源版本 | 验证、发布、恢复 |
| 知识版本 | 有效内容、条件、来源与确认状态 | 发布、读取响应 |
| 发布快照 | 选中的知识版本与使用状态 | 下游接收和验证 |
| 接入主体 | 客户、调用方、实际人员及动作授权 | 任务、确认、读取 |

关键约束：可追溯不是只保留聊天记录。每项执行必须能关联来源版本、决策、规则版本与修订集；无法建立依据链时，不能声称处理已验证。

问题检测、事实确认和执行授权是不同对象。业务确认不能扩大来源读取权限。

## 六、状态设计与失败处理

### 6.1 任务

等待处理、分析中、等待决策、修复中、验证中、待发布、已完成；另有暂停、失败、已取消和部分完成。

等待决策只阻塞相关处理，其他已授权独立事项可以继续。取消是停止未执行工作，不自动撤销所有已执行动作；系统展示已完成部分及可恢复方式。

### 6.2 规则

草案、待确认、试运行、已生效、已替代、已暂停、已撤销。批准一次具体修订和批准持久规则分开记录。

### 6.3 知识

待确认、已确认但未发布、当前生效、未来生效、已替代、已撤销、受限。状态与业务生效时间分开管理，不把最新编辑时间当作生效时间。

### 6.4 必须处理的异常

| 异常 | 对用户呈现与系统行为 |
|---|---|
| 无法解析 | 指出文件和原因，保留未检查状态 |
| 意见不清楚 | 先复述理解并追问，不能自行扩展规则 |
| 无人回答 | 保存待办，继续独立的已授权事项 |
| 规则互相冲突 | 展示范围与矛盾，暂停相关执行 |
| 原资料在处理时改变 | 重新核对来源版本，不能覆盖新内容 |
| 模型超时或返回不完整 | 保存任务检查点，不标为完成 |
| 修复验证失败 | 阻止相关发布，恢复或重新提出方案 |
| 预算不足 | 说明已完成和剩余范围，等待预算选择 |
| 来源权限撤回 | 立即按授权限制访问，清理受影响缓存和输出 |
| 下游同步失败 | 保留本地发布，明确失败目的地并重试 |

## 七、AI 内部工作方式

用户看到一个专用 Agent，不需要理解内部是否包含多个模型调用。实现上将工作拆成可验证的职责，而不是一次提示词要求完成所有任务。

建议职责：任务规划、资料盘点与解析、候选关系查找、问题诊断、决策归并、对话澄清、规则提案、修订执行、验证、发布与持续检查。

这些职责不是承诺为每一步创建一个独立 Agent。能由程序可靠完成的动作优先程序执行，需要语义理解的部分再调用模型，便于控制成本和复现。

处理计划允许 AI 根据资料变化调整，但必须保留范围、预算、检查点和授权。验证不只是让同一个模型再说一次“正确”：还要检查源文定位、引用完整、版本一致、规则适用和约定测试案例。

“执行规则”的内容不能从任意原文直接取得。原文中的命令只作为待分析资料，可信执行范围来自已授权的产品状态。

## 八、数据与成本设计

保留 v0.1 的四层结构：来源登记、内容与证据缓存、治理状态、有效知识视图。默认逻辑汇聚，可按任务缓存所需内容，不先复制全企业资料。

初始成本来自资料读取、解析、必要语义分析和规则建立；维护成本来自新增内容、变化部分和关联影响。查询成本来自读取当前结果，不应为同一结果再次全量清洗。

增量触发同时覆盖来源、规则、处理方法与权限变化。缓存失效不能只依赖文件名或修改时间。

候选筛选减少全库比较，但引入漏检风险；范围说明要区分全量检查、主题检查、抽样检查和按需核查。预算较低时不宣称全库审计。

聊天只携带当前决策所需证据，任务状态和已完成结果留在后台。重要语义判断不能只依赖摘要；需要时重新读取相关原文。

费用页展示首次整理、日常维护、复杂解析和开放调用等成本类别。实际金额与套餐需实测，概念演示不虚构性能、Token 节省比例或自动化率。

## 九、开放接口设计原则

首版接口范围建议：提交任务、读取任务、读取问题、提交意见、获取提案、获取有效知识和发布结果。写入能力逐项授权，不在一个通用接口中隐含全部权限。

对外任务返回任务标识和状态，后台完成后再查询或通知。未解决问题返回澄清请求；外部 Agent 可以转述，但最终发布确认需要可验证的授权身份。

有效知识响应包含：内容、来源、发布版本、适用条件、生效时间、当前状态和缺少的上下文。不能只返回相似文本让调用方自行猜测。

变化通知建议区分：知识已发布、知识已撤销、任务等待决策、任务完成、目的地同步失败。通知只发送必要标识，读取正文时再次校验权限。

API 和 MCP 共用同一执行服务。首个适配对象由现有客户真实需求选择，不先承诺全平台接入。

## 十、完整示例：首次整理到第二批资料

以下均为模拟：

1. 项目接入产品说明、两版报价、会议纪要、历史合同和一个无法可靠解析的扫描件。
2. AI 找出报价差异及交付周期冲突，无法解析的扫描件列为未检查，不根据文件名猜测内容。
3. 客户解释：新客户采用已批准的新报价，老客户采用有效合同；渠道客户另行确认；交付规则按批准的生效时间执行。
4. AI 区分价格与交付规则，确认均仅限当前项目，展示影响；客户批准价格规则，交付事项仍待确认。
5. 系统修复派生价格知识，验证老客户与新客户案例；渠道客户测试应返回需要确认，而不是统一价格。
6. 客户发布价格知识；交付冲突和扫描件继续保持待处理。原始资料不删除。
7. 外部 Agent 查询新客户价格，取得当前已发布报价及出处；查询渠道客户价格，取得澄清要求。
8. 第二批已批准报价进入，系统复用项目价格规则，在既有授权允许的范围内更新派生提案；发布是否自动取决于单独授权，不因为规则曾获批准就自动发布新事实。
9. 若下游采用导出副本，系统记录同步和验证状态；离线副本不宣称可即时撤回。

此例刻意允许部分发布，展示问题、规则、修订和发布不是同一个完成状态。

## 十一、首版与完整产品的边界

| 能力 | 首版 | 后续完整产品 |
|---|---|---|
| 资料输入 | 上传及有限文本类型 | 优先云文档连接器、扫描件与多模态 |
| 业务范围 | 一个项目／主题 | 授权后的跨项目与部门协作 |
| 主动处理 | 首批问题类型和指定范围 | 持续监测、多场景规则与任务 |
| 规则 | 对话提案、确认、试运行、版本 | 分层规则、共享模板、复杂冲突处理 |
| 修复 | 派生版本 | 授权写回与跨系统一致性 |
| 发布 | 单项目有效视图和导出 | 多目的地发布、回执和撤回机制 |
| 开放 | 统一任务与读取 API、一个适配 | MCP 扩展、更多客户端与 SDK |
| 团队 | 所有者／协作者 | 企业角色、审批、审计和部署 |

首版不能删减到“只给报告”，必须包含规则形成、修复与第二批复用。完整产品不能理解为第一版同时实现全部能力。

## 十二、概念演示与评审方式

本轮概念演示可切换工作台、整理任务、资料来源、有效知识、处理规则、发布版本和 Agent 接入。

演示一个有限状态流程：提供业务意见、确认项目规则、生成修复版本、确认发布、加入第二批资料。所有结果为预设示例，不调用模型，不读取资料，不连接真实 Agent。

演示目的是检查：导航是否让人理解产品，对话是否真的减少手动操作，规则是否有明确范围，修复成果是否可见，发布与开放接入是否能说清楚。

可探索的设计方向：默认从待决策事项进入，或默认从任务对话进入；证据并列展示，或按需展开。它们只是展示方式变化，不改变授权和状态规则。

优先评审以下五点：

1. 用户进入后是否能立即理解“AI 在替我做什么、我只需决定什么”？
2. 是否认同派生修复默认不改原件，以及规则批准与知识发布分开？
3. 有效知识是可交付资产，还是只需要修复客户原系统？二者可以兼容，但首版需明确优先级。
4. 首个外部 Agent 是读取有效知识，还是委托整个整理任务？
5. 当前客户能否提供一个资料集，用来验证首次整理和第二批规则复用？

## 十三、进入研发前的产物

本轮只完成产品设计讨论，不改现有业务代码。方向确认后再交付：页面级交互规格、对象字段与状态定义、首批检测与修复测试集、接口契约、预算测量方案和任务拆分。

验收仍以客户人工总时间、修复正确性、例外识别、第二批复用和完整成本为准。可点击演示不能替代真实资料验证。
