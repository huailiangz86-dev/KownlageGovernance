# 资料治理 Agent：竞品扫描

日期：2026 年 9 月 27 日  
状态：定位与原型评审材料，不构成市场规模、定价或功能完整性结论。

## 结论

“主动维护资料、发现陈旧内容、提出修订并由人审核”已经不是空白品类。首版不能以“有 AI、会检测冲突、有人在环”作为差异化。

仍值得验证的切入点是：对一个明确项目范围，把多份资料中的同一业务歧义归为一个决策；把该决策保存为有范围、条件、例外和版本的规则；生成可恢复的派生修订；并将修复、发布及下游同步验证分成独立状态。这个说法目前是产品假设，不是已证实壁垒。

## 已核查产品

| 产品 | 已公开能力 | 与本产品的重叠 | 对首版的影响 |
|---|---|---|---|
| [Slite Agent](https://slite.com/solutions/self-maintaining-documentation) | 在连接工具中比对文档、发现漂移、给出拟议修订，并由负责人审核；可按周期复查。 | 直接覆盖“资料会陈旧、AI 主动发现、建议修复、人审”的核心体验。 | 原型和试点必须证明不只是逐文档 triage：要展示问题聚合、适用条件、规则复用与发布控制。 |
| [Guru Knowledge Agents](https://help.getguru.com/docs/verifying-and-unverifying-cards) | 对卡片和外部来源做自动验证／撤销验证；有责任人、质量日志、内容及行为规则、近重复识别。 | 资料可信状态、规则、责任人与持续检查均有重叠。 | 不能用单一“已验证”状态描述业务事实；有效知识需能并存不同客户、合同及生效时间的条件。 |
| [Atlan Knowledge Folders](https://docs.atlan.com/product/capabilities/governance/knowledge-folders/concepts/knowledge-folders-and-files) | 将非结构化文件纳入受治理目录、血缘与权限；公开文档说明知识综合 Agent 将做冲突版本解析、去重和文件夹提议。 | 受治理的非结构化来源、下游 Agent 上下文、权限与溯源高度相关。 | 不宜承诺先复制全企业资料；保留逻辑汇聚、来源级权限与证据链，并以小项目资料集起步。 |
| [Glean Agent Builder](https://www.glean.com/ai-agent-builder) 与 [Knowledge Profiles](https://docs.glean.com/administration/managing-agents/knowledge-profiles) | 在大规模连接器、企业图谱、权限感知上下文和 Agent 构建之上提供工作流；可限定 Agent 检索范围。 | 开放 Agent、权限、上下文范围与企业扩展路径有重叠。 | 不把“另一个通用 Agent 平台”列入首版；开放接口应先围绕治理任务与有效知识，而非 Agent 编排画布。 |

## 原型调整原则

1. 首页把“1 个问题组影响 3 处资料”作为主提示，而不是逐文件的批准队列。
2. 证据区域明确“文件更新更晚不等于权威”，显示合同、客户类型与生效时间共同决定适用性。
3. 继续保持规则确认、派生修复、知识发布与下游同步为不同状态；不使用一个笼统的可信徽章概括所有业务条件。

## 需要用真实试点回答的问题

- 真实用户是否愿意把少量业务判断交给这种规则化流程，而不是在现有知识库中逐条审核？
- 第二批未见资料能否正确复用规则，同时识别例外而不错误推广？
- 与 Slite/Guru 类维护流程或客户当前方式相比，人工总时间、错误修复率和可恢复性是否更好？
- 哪类小团队资料最需要“适用性＋发布控制”，并愿意为该结果付费？

## 原型落实（v0.4）

在既有问题组、规则、派生修复和发布演示之上，v0.4 增加四个可检查状态：

- 工作台：持续维护范围、业务负责人和“规则复用不自动发布”。
- 发布页：本地生效、下游接收与下游验证分离，并显示发布责任。
- 预算与权限：来源／规则／权限变化触发增量检查；冲突、例外和预算不足升级为决策。
- Agent 接入：读取、提案与写入权限分离，外部 Agent 的意见须核验。

这些设计吸收了竞品的持续维护、责任归属和受控范围做法；它们是待验证的体验方案，不代表已经实现相应后端能力。
