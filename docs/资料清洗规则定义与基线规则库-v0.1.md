# 资料清洗规则定义与基线规则库 v0.1

## 1. 目的与边界

本规则库把“资料有问题”的判断拆成可解释、可试运行的检测规则与受控处理规则。它服务于项目内的来源版本、派生修订和有效知识；不以文件名、最后修改时间、模型置信度或单一相似度分数直接删除、替代或发布任何内容。

规则的输出首先是**发现**，不是事实结论。发现只有在证据、适用条件、权限和人工确认（如需要）都满足后，才能产生修订或影响有效知识。原件永不因本规则库自动删除或覆盖。

适用对象：可解析的 Markdown、TXT、DOCX、文本型 PDF 及其内容片段。扫描件、不可读附件和表格解析不足的资料应产生“未检查”或解析问题，不能被标为“正常”。

## 2. 问题分类：从“重复”扩展到“可用性”

每个问题类型必须有明确的判定边界，避免把“文件较新”或“看起来相似”误作替代关系。

| 类别 | 问题类型 | 何时成立 | 默认处理 | 不可据此推断 |
|---|---|---|---|---|
| 身份与重复 | `duplicate` | 同项目内来源版本的正文 SHA-256 相同 | 复用解析结果，关联来源，不重复索引或生成知识 | 两个来源中哪一个更权威、另一个可删除 |
| 身份与重复 | `near_duplicate` | 文本/结构高度相似且表达同一命题，但哈希不同 | 建立候选簇并展示差异 | 版本替代、内容完全相同 |
| 版本关系 | `supersession_candidate` | 有明确“替代/废止/修订”依据，或在同一权威链中较新内容覆盖同一命题与范围 | 生成为“全部/部分替代候选”，等待确认或已生效规则 | 同名、较晚上传或较晚修改即为替代 |
| 时间有效性 | `expired_content` | 适用内容的 `effective_to` 早于业务日期，或已确认的有效期已结束 | 从“当前有效”候选中排除，保留历史与证据 | 文件应被删除、其他段落同样失效 |
| 时间有效性 | `future_content` | `effective_from` 晚于业务日期 | 标为未来生效，不作为当前答案 | 内容错误或应废弃 |
| 时间有效性 | `review_overdue` | 来源/知识明确配置了复核周期，且超过 `last_reviewed_at + interval` | 创建复核任务，降低新答案的优先级或要求澄清（按规则） | 内容已经过期或被新文件替代 |
| 内容关系 | `content_mismatch` | 标题、标签、声明用途或目标问答与正文证据不一致，或正文不能支持其被引用的结论 | 标注不匹配片段和预期上下文，要求重新分类/确认 | 整篇资料无用、某个事实为假 |
| 内容关系 | `coverage_gap` | 目标问题所需的必要条件、对象、日期或结论在可读资料中缺失 | 返回澄清/补资料请求 | 用语义相近内容补全事实 |
| 适用性 | `applicability_gap` | 内容没有覆盖当前客户、地区、产品、版本、角色或业务日期，或条件互相矛盾 | 不在该上下文输出，返回所缺条件 | 内容对所有场景无效 |
| 权威性 | `authority_gap` | 内容缺少此类结论所需的批准状态、责任主体、来源等级或签发信息 | 限制为线索/草稿，不作为正式依据 | 内容必然错误 |
| 一致性 | `conflict` | 相同命题、相容上下文内存在不相容的事实、数值、条件或状态，且都具备可读证据 | 建立问题组，阻止相关修订/发布 | 任一来源自动胜出 |
| 可用性 | `unsuitable_for_use` | 内容因权限/数据分类、用途限制、解析不完整、不可追溯、仅为讨论稿或无法形成可验证结论，而不适合目标用途 | 限制读取或排除出对应有效知识视图；保留来源 | 应删除原件，或其对其他用途也不可用 |
| 技术质量 | `parse_failure` | 必要正文或定位未能提取，且重试/降级仍失败 | 标为未检查，报告失败原因 | 没有发现问题或内容没有价值 |

`content_mismatch` 解决“文章内容对不上”：它必须同时记录**期待的命题/用途**和**正文实际证据**。例如文件名为“2026 价格表”、正文却是会议纪要，只能标为元数据与正文不匹配，不能据此断言会议结论无效。

`unsuitable_for_use` 解决“内容不适合用”：它按目标用途判定。例如未批准的讨论稿可以作为冲突线索，不能作为对外报价依据；含受限个人信息的材料可在受权审计中使用，却不能进入销售 Agent 的知识视图。该类型必须带 `target_use`，不得作为泛化的“垃圾内容”标签。

## 3. 规则对象与统一定义

规则分为两层，且必须分别版本化：

1. **检测规则（detector）**：从来源、片段、元数据和上下文生成发现；允许确定性计算与受约束的语义判断。
2. **处理规则（policy）**：在发现成立时决定是否聚合、标记、创建派生修订、限制读取或请求人工决策；不得绕过动作分级和发布确认。

一个规则版本至少由以下字段组成。界面可以用表单或自然语言协助填写，但服务端保存并校验结构化定义。

| 字段组 | 必填内容 | 设计要求 |
|---|---|---|
| 身份与版本 | `id`、名称、版本、状态、所有者、变更说明 | 修改任何判定或动作都新建版本；禁止覆盖历史版本。 |
| 作用范围 | `project_id`、对象类型、资料分类、目标用途、允许的调用方/数据分类 | 默认仅一个项目；选择器只能缩小权限与范围。 |
| 输入契约 | 必需字段、允许来源状态、业务日期和上下文要求 | 缺字段返回 `indeterminate`，不得把未知当作命中。 |
| 检测逻辑 | 确定性谓词、语义任务、阈值、比较窗口、关系键 | 语义规则必须声明模型/提示词/嵌入版本、阈值和回退方式。 |
| 证据契约 | 最少证据数、来源等级、片段定位、正反证据要求 | 每个命中至少能定位到 `source_version_id + locator`。 |
| 结果与动作 | `matched / not_matched / indeterminate` 的处理、风险级别、允许动作 | 发现动作与业务动作分离；默认仅生成发现。 |
| 例外与冲突 | 排除条件、优先级、与其他规则的互斥/组合关系 | 例外优先于一般规则；无法比较范围时建立冲突。 |
| 不确定策略 | 置信阈值、人工复核门槛、降级输出 | 不确定只能创建候选、复核或澄清，不能自动替代。 |
| 验证 | 正例、反例、边界例、例外例、未见验收集 | 规则激活前测试；第二批资料只作验收，不能反向调阈值。 |
| 生命周期 | `effective_from/to`、复核周期、停用/撤销影响 | 规则到期后停止新动作，但保留历史审计。 |

### 3.1 推荐的结构化表达

以下是 `TIM-001` 的示意，不要求用户直接编写 JSON；它是规则编辑器与执行器之间的稳定契约。

```yaml
id: TIM-001
version: 1
kind: detector
name: 已结束有效期的内容
scope:
  project_id: "<project>"
  object_types: [knowledge_claim, content_segment]
  target_uses: [current_answer, publication]
input_contract:
  required: [business_date, effective_to, source_version_id, locator]
logic:
  all:
    - field: effective_to
      operator: before
      value_from: business_date
evidence:
  min_count: 1
  locator_required: true
outcomes:
  matched:
    finding_type: expired_content
    severity: high
    actions: [exclude_from_current_candidate, create_review_item]
  indeterminate:
    actions: [request_context]
exceptions:
  - when: { field: record_kind, equals: historical_archive }
    actions: [retain_as_history]
tests:
  required_sets: [positive, negative, boundary, exception, unseen_acceptance]
```

处理规则应引用发现而非重做检测。例如：`POL-EXP-001` 可规定“已确认来源等级为 `approved` 的 `expired_content` 在当前回答中排除，但历史查询可返回，并保留替代关系”；它不能把“上传时间较新”写成失效条件。

## 4. P0 基线规则包

下表是首版应随产品提供、可在项目内启停和配置阈值的规则。它们不是跨项目自动生效的业务规则；项目可对每条规则选择目标用途、复核周期和动作权限。

| ID | 触发条件（简写） | 发现/处理结果 | 人工确认要求 |
|---|---|---|---|
| `DUP-001` | 同项目、正文 SHA-256 相同 | `duplicate`；复用解析，不重复索引 | 不需要 |
| `DUP-002` | 同类型、相似度达候选阈值且命题相近 | `near_duplicate`；列出差异 | 合并、替代或降权需要 |
| `REL-001` | 明确替代/废止语句 + 同一命题/范围的可定位证据 | `supersession_candidate`；区分全量/部分替代 | 影响正式知识时需要 |
| `REL-002` | 同一权威链、较高版本且逐项覆盖旧命题 | `supersession_candidate`；输出覆盖矩阵 | 影响正式知识时需要 |
| `TIM-001` | `effective_to < business_date` | `expired_content`；排除当前候选，保留历史 | 不需要排除；撤销发布依发布权限 |
| `TIM-002` | `effective_from > business_date` | `future_content`；不可作当前答案 | 不需要 |
| `TIM-003` | 明确复核周期到期 | `review_overdue`；创建复核，不下失效结论 | 不需要创建任务 |
| `SEM-001` | 声明主题/用途与正文支持的命题不一致 | `content_mismatch`；定位预期和实际内容 | 重新分类、修订元数据需要 |
| `SEM-002` | 目标任务的必要命题在可读范围内无充分证据 | `coverage_gap`；请求缺少的资料/条件 | 不需要 |
| `APP-001` | 请求上下文不满足客户/地区/产品/角色/日期条件 | `applicability_gap`；不返回该结论 | 不需要 |
| `AUT-001` | 正式用途缺少批准、签发人或来源等级 | `authority_gap`；降为线索 | 升格为正式依据需要 |
| `CON-001` | 相容上下文内的已定位断言不相容 | `conflict`；阻断关联发布 | 选择结论或规则需要 |
| `USE-001` | 数据分类、用途限制、可追溯性或文本完整性不满足目标用途 | `unsuitable_for_use`；限制对应视图 | 放宽限制需要 |
| `QLT-001` | 解析、定位、必要字段或来源读取不可用 | `parse_failure` / 未检查 | 不需要 |

## 5. 判定与处理的安全护栏

1. **时间不等于新旧。** 只有业务有效期可以判定 `expired_content`；文件系统修改时间、上传时间和发布日期只能排序复核候选。
2. **相似不等于重复。** `DUP-002` 的输入必须保留差异段、比较方法和阈值；不得自动合并、覆盖或抑制任一来源。
3. **文章标题不等于正文。** `SEM-001` 必须比对声明用途与正文命题；附件、章节和历史说明允许作为例外，不可只按标题判错。
4. **局部失效不传播。** 失效、替代、受限和不适用的最小对象是可定位断言/片段；只有明确全篇范围才可影响整份来源。
5. **内容不可用须说明用途。** `USE-001` 必须给出 `target_use` 与失败条件；不能把草稿、意见或受限内容静默删除。
6. **语义模型只做受约束判断。** 它的输出必须带模型/方法版本、置信度与证据；低于阈值、证据不足或互相矛盾均为 `indeterminate`。
7. **发现不能绕过业务决策。** `conflict`、替代候选、范围扩大、事实修订和发布遵循 PRD 的 L2/L3 授权；检测规则没有修改原件的能力。

## 6. 规则执行流水线

```text
来源版本/任务上下文
  → 输入完整性与权限检查
  → 确定性检测（哈希、日期、状态、条件）
  → 候选召回（近重复、替代、主题关系）
  → 受约束语义判定与证据定位
  → matched / not_matched / indeterminate
  → 问题归并与影响预览
  → 已生效处理规则决定：标记、限制、修订提案或请求决策
  → 独立验证与发布
```

执行记录至少包含：输入来源版本集合及哈希、上下文（含业务日期）、规则/模型/解析器版本、候选数与阈值、每个结果、证据定位、耗时、成本、操作者和授权快照。规则升级或输入来源改变后，相关缓存和发现应标为待重算，历史结果不可静默改写。

## 7. 规则编辑与运营方式

规则编辑器应采用“自然语言提案 + 结构化预览 + 试运行”的流程：

1. 用户描述意图，例如“合同到期后不再给销售助手引用，但仍能在历史审计中查到”。
2. 系统生成草案，并显式展示目标用途、日期字段、例外、动作等级、需要确认人及不能判断的情况。
3. 选择一组已知正例、反例、边界例与例外例试运行，展示命中、漏报候选和影响范围；试运行不改知识。
4. 业务确认人确认范围与动作后激活项目规则；系统在第二批未见资料上统计命中、例外、误报与人工返工。
5. 规则出现误推广、条件变化或证据来源撤回时，暂停或撤销；系统列出受影响的发现、修订与发布快照，必要时发起复核或撤回流程。

对每一条规则，界面都应显示“它检测什么”“它**不**代表什么”“命中后会做什么”“哪些情况会交给人”。这比让用户维护一个无法解释的总分更适合资料治理场景。

## 8. 最小验收数据集

每一类规则至少准备：正例、反例、边界例、例外例以及不参与设计的第二批验收例。首批数据集应覆盖：

- 同哈希但不同文件名；同名但内容不同；高度相似但一份包含客户例外；
- 部分替代与全量替代；版本号更高但缺少批准；
- 已过有效期、未来生效、没有有效期、复核过期但仍可能有效；
- 标题是报价而正文是会议纪要；正文支持产品 A 却被用于产品 B；
- 草稿、已批准文件、受限附件、无法定位的摘要；
- 相同上下文的冲突数值与不同客户/日期下的合法差异；
- 解析失败、权限撤回、缺少业务日期或客户类型。

验收报告需要同时给出发现准确性、未检查率、人工确认率、规则在未见资料上的误报/漏报、规则动作造成的修订/撤回数量。不能只报告模型相似度或规则命中率。
